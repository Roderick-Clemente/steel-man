The hook never fired in either case — once because the model declined, once\nbecause the matcher missed the tool.\n\n- Never conclude \"the guard works\" from a run where a strong model simply behaved.\n  Re-run with the **cheapest cross-family executor available** and try to break it.\n- H3 (role-tiered cheaper executors) is a *design goal*, so weak-model behavior is the\n  case that matters, not the exception.\n- Name-based matchers (`Edit|Create|ApplyPatch`) are necessary but not sufficient — a\n  shell write (`Execute` + `sed -i`, `python -c`, `>`, `tee`) walks through any\n  tool-name list. The fix is a guard that **inspects reality** (the command, or the\n  post-tool file state), not the tool name.\n\n## 7. Assert on reality, never on exit code\n\nThe platform's default failure mode is **silent green** — it reports success while\ndoing nothing, being blocked, or being misconfigured (four independent sightings in\nPhase 0). Therefore:\n\n- Never trust `exit 0` or a plausible result string as proof work happened.\n- Assert on the hook log, per-tool `is_error`, file SHAs, and captured output — the\n  actual artifacts of what occurred.\n- A finding is \"reproducible from a clean shell\" or it is not evidence.\n\n## 8. When scope shifts, name it — don't absorb it silently\n\nDuring Phase 3.2 (evidence provider), the orchestration gap was discovered: the\nprocess was ad hoc, run by an AI agent manually executing commands instead of by\na scripted pipeline. That gap was a framework-level concern (PRD Act 2:\nautomation), not a 3.2-specific concern (externalize the evidence tier). It got\nbuilt inside 3.2 because it emerged naturally, but it should have been its own\nloop with its own prompt.\n\nThe rule when scope shifts mid-phase:\n\n1. **Name it.** If the work you're doing is not what the phase's RUN-PROMPT\n   scoped, say so explicitly. Don't silently absorb it.\n2. **Decide: absorb or push out.** Small, in-scope additions that emerge\n   naturally can be absorbed (log in ASSUMPTIONS.md). Larger scope shifts that\n   are really a different concern should be **pushed out** to their own loop /\n   prompt / phase — record it as a follow-on, finish the current scope, then\n   give it the full treatment separately.\n3. **Record the decision.** Either way, the scope shift and the decision go in\n   the phase's ASSUMPTIONS.md or KNOWN-ISSUES.md. A scope shift that nobody\n   recorded is the same defect as a silent green: it happened, but there's no\n   evidence it was considered.\n\nThe temptation is to keep building because you're already in the flow. The\ndiscipline is to stop, name the shift, and decide whether it belongs here or\nin its own loop. Most scope shifts want their own loop.\n\n\n## 9. If it's not scripted, it didn't happen\n\nA phase that runs its `droid exec` invocations by manually copy-pasting\ncommands has no reproducible evidence. The orchestration script must be the\ndefault way reviews are run. A RUN-COMMANDS.md file is documentation for the\nscript, not a substitute for it. If the script doesn't exist yet, the first\ndeliverable of the phase is to build it — **bounded to the phase's actual\nrepeat surface**, not a full panel orchestrator by default.\n\n*Exception:* pure probe spikes (Phase 0-style) may run manually — they are\none-off capability checks, not repeatable loops.\n\n*Rationale:* Phases 1-3 ran manually. The orchestration script was built in\n3.2 and partially works. This rule makes \"script the loop\" the default, not\nthe retrofit.\n\n\n## 10. Telemetry rows are written by the script, not by the operator\n\nFrom adoption forward, multi-invocation phases must emit `runs.jsonl` (and\n`findings.jsonl` / `dispositions.jsonl` when applicable) from the\norchestration script as part of each `droid exec` invocation, not appended\nmanually after the fact. Committed envelopes + auditable reconstruction\nrecipes (e.g. `gen-telemetry.py`) remain valid evidence for past phases and\ndisaster recovery. Phase\n3's rows were overwritten. Phase 0.5 and Phase 1 used `RUN-LEDGER.md` as\ntheir SoR, which was valid at the time. This rule is forward-looking, not\nretroactive.\n\n\n## 11. Exit criteria are checked, not assumed\n\nA phase's exit criteria must be checked against actual artifacts before the\nphase is declared complete. \"Invalid RED cases are rejected\" means at least\none invalid-RED case was run and rejected — not that the classifier script\nexists. \"Replayable demo\" means a demo artifact exists — not that the wiki\nentry is comprehensive. \"Local PR creation\" means a PR was created — not\nthat the README says \"present the slice.\"\n\n*Rationale:* Phase 1 declared \"invalid RED cases are rejected\" as met, but\n`valid-red.py` was never run. Phase 3 declared completion without a demo,\nbaseline comparison, or PR. The exit criteria exist to be checked, not to\nbe interpreted.\n\n\n## 12. Unexercised safety paths are named gaps, not phase blockers\n\nIf a phase's purpose is to test a mechanism (reconciliation, validation\nblocking, retry/re-plan), and the mechanism was not triggered (e.g., the\nplan converged on round 1, or all validators returned ACCEPT), the phase is\n**complete with a clean null result** — this is valid data per PRD §13 (\"a\nclean null result is valid data; models disagree at least once is NOT a\nsuccess gate\"). Don't give the executor the answer\n\nThe executor prompt must describe the problem and the constraints, not the\nimplementation. If the prompt contains the exact code change to make, the\nexecutor is a `sed` command, not an independent implementation. The\ncheap-executor seat's value (H3) depends on the executor solving the\nproblem, not applying a known fix.\n\n*Rationale:* Phase 1's executor prompt specified the exact one-line fix.\nThe executor's 4-turn run confirmed it was mechanical. The H3 cost\nhypothesis (cheap executors can do the work) was never genuinely tested\nuntil Phase 4 Track B H3 validated it.\n\n\n## 14. Use the adapter shim and the model-discipline wrapper\n\nAny script that reads `droid exec` envelope data must go through\n`tools/adapters/factory.py` (or the equivalent vendor adapter). Compose existing primitives; build in chunks; fix ergonomic friction inline\n\nA new build's first question is **\"what existing primitives compose this?\"**\n— not \"what do I write from scratch.\" The repo already ships tools whose\nauthors faced the same problem. A NEW abstraction that ignores them is\neither reinvention (rule §14 silent-scope-lie), duplicate directory\n(operational debt), or a missed reuse.\n\nConcretely, before writing code:\n\n1. **Compose first.** ``grep -l`` the project for the nearest existing\n   primitive (``tools/``, ``phase-1/scripts/``, ``phase-3.2/evidence/``,\n   the model-discipline conventions). A standing rule reads on\nevery agent entry — a prompt does not.\n\n## 19. Commit when the recommendation is clear; do not force the operator to choose\n\nWhen you have a recommendation and you can articulate the trade-offs of\nthe alternatives, **commit to the recommendation** — don't ask the\noperator to pick. Surface the WHY (one short paragraph) and ship. The\n3-option \"you choose\" question is appropriate only when *no* option is\nclearly best — when the trade-offs are roughly symmetric across user\npreference and you genuinely cannot rank them.\n\n*Anti-pattern:* offering three labeled choices for a decision whose\ninternal ranking the agent could state in one sentence. The operator\nbecomes the forced chooser of something the agent already ranked. The\nclaude-opus-5 session that produced chunk 11 fallback questions three\ntimes in one turn earned this rule; the operator's exact response was\n\"part of the skill should be don't do that cuz its annoying lol.\"\n\n*When multiple options ARE legitimate* — for example, a tradeoff with\nreal operator values (cost vs. reach vs. simplicity) that the agent\ncannot rank without the operator's preference — then ask, but make it\none question, framed in operator language, not three agent-proposed\noptions mirrored back.\n\n*Rationale:* agents with strong defaults save operator attention. Any mutation invalidates the gate and requires review.\n6. **Blocking validation:** a rejected chunk cannot be marked complete.\n7. **Explicit degradation:** if family identity, context isolation, test locking, or artifact capture cannot be guaranteed, the run stops rather than silently weakening the method.\n8. **Human merge:** the system may create a branch, local commits, and a PR; a human approves the merge.\n\n### What “model family” means\n\nFamily is declared model provenance, not a marketing label or cost tier: Anthropic/Claude, OpenAI/GPT, Google/Gemini, DeepSeek, and so on. Open-weight derivatives must declare their upstream base family. Unknown provenance is treated as unknown and cannot satisfy a hard separation constraint.\n\nThe plugin owns a versioned `model-families.json` map. Every run records resolved model ID, provider, family, role, and whether a fallback occurred. A fallback that violates a role constraint stops the run.\n\n**Provenance is maintained by hand, not detected.** Many hosted providers will not declare an upstream base family, and nothing in the runtime can verify a claim of provenance. So `model-families.json` is a curated file with an owner and a review date, not an inference. Any model absent from the map resolves to `unknown`, and `unknown` cannot satisfy a hard separation constraint — it stops the run rather than being optimistically admitted. End-to-End Workflow\n\n```text\nINTAKE / PREFLIGHT\n  ↓\nGROK — planner drafts problem analysis, acceptance criteria, risks, test strategy\n  ↓\nBLIND REVIEW — different-family reviewer emits structured findings\n  ↓\nRECONCILE ◄──────────────┐\n  │                      │ revise, re-review (bounded)\n  └─ unresolved risk? ───┘\n  ↓\nTEST DESIGN — independent behavioral tests and expected RED signatures\n  ↓\nCHUNK / LOCK — final dependency graph, test hashes, commands, rollback\n  ↓\nEXECUTE — per chunk: verify RED → implement GREEN → refactor\n  ↓\nVALIDATE — different-family validator; approved spec + diff + repo + evidence\n  │\n  ├─ reject → bounded retry → re-plan or human gate\n  └─ accept\n  ↓\nREPORT / PR — audit bundle, comparison metrics, human merge decision\n```\n\n### 5.1 Intake and preflight\n\nThe input may begin as a short goal, but execution cannot begin from an unreviewed one-line prompt. Preflight produces or verifies:\n\n- source commit and isolated sprint branch/worktree;\n- clean handling of any pre-existing user changes;\n- baseline build, lint, and test commands plus current results;\n- explicit acceptance criteria and out-of-scope boundaries;\n- allowed files, tools, credentials, network access, and autonomy level;\n- budget, timeout, retry limit, and human-gate policy;\n- resolvable model IDs and valid family separation;\n- artifact directory writable and excluded from product behavior where appropriate.\n\nIf baseline tests already fail or are flaky, the run records that state and either narrows the gate to an approved test subset or stops for human disposition. Syntax errors, import errors, missing fixtures, unavailable services, empty test selection, timeouts, and unrelated assertion failures are **invalid RED**.\n\nRefactors, docs-only changes, test-only cleanup, and fixes with an already-failing test may receive a documented exception. This is entered as the\ntrigger for the phase, a finding to be measured, not a claim already proven.\n\nThe bet: compress the human seat from \"read every finding\" to \"rule only on genuine disagreement\", without breaking invariant #1. Candidate mechanisms, all sitting on machinery that already exists (`telemetry/findings.jsonl`, `telemetry/aggregate.py`, the self-declared-risk input from Probe 8):\n\n- a review **panel** rather than a single reviewer, with thinking-hats-style lenses (caution, facts, alternatives) assigned *across families* so the hats add lens coverage while family separation stays the independence control. A panel that agrees can be wrong together, so the calibration record must include panel-agreed-but-wrong cases caught later, or the knob will tune the human out on the strength of agreement that was never evidence, the same \"a run's own account of itself is not evidence\" principle applied to the panel instead of the executor.\n\nDistinct from Phases 6 and 7: Phase 6 generalises the loop across stacks;\nPhase 7 hardens the loop's own invariants at no new behaviour; Phase 8 is\nnew behaviour aimed at the *operator's* cost, and is deliberately kept\n**outside the measured 0–6 arc**. Until the MVP is run, this phase carries no committed target: the pain it addresses has to be measured before it can be sized.\n\n---\n\n## 12. v1 Acceptance Criteria\n\n- [ ] Phase 0 proves or disproves every Factory capability on which v1 depends.\n- [ ] A run starts from a recorded source commit in an isolated branch/worktree and preserves unrelated user changes.\n- [ ] Effective model ID/provider/family is recorded for every role, and invalid separation stops before code execution.\n- [ ] The plan cannot advance with an unresolved blocker/high finding or without an exact plan-hash approval.\n- [ ] Behavior-changing code cannot begin until a valid behavioral RED is captured.\n- [ ] Test content is locked from RED through GREEN; executor test edits are blocked.\n- [ ] Every chunk has explicit scope, observable criteria, commands, rollback, and evidence.\n- [ ] Validator context excludes the executor transcript but includes read-only repository state sufficient to find integration issues.\n- [ ] A validator rejection blocks completion and exercises at least one retry, re-plan, or human-decision path in a controlled drill.\n- [ ] The run can resume safely after interruption without duplicating completed mutations.\n- [ ] The final report includes findings/dispositions, model assignments, test evidence, retries, elapsed time, and credit/token usage when available.\n- [ ] The system creates a human-reviewable PR or local branch/commit bundle and never auto-merges.\n\n---\n\n## 13. Evaluation Design\n\nProduct acceptance and thesis validation are separate. The plugin may work even if a hypothesis underperforms.\n\n### Comparison\n\nRun at least three bounded pilot tasks from identical repository snapshots:\n\n1. single frontier model, self-planned and self-reviewed;\n2. all-frontier separated roles; and\n3. role-tiered adversarial workflow.\n\nUse the same goals, acceptance criteria, tool permissions, maximum elapsed time, and hidden tests. Counterbalance task/order where possible. Do not tell executors the hidden tests.\n\n### Metrics\n\n| Metric | Why it matters |\n|---|---|\n| Hidden acceptance-test pass rate | Primary external correctness measure — see note below |\n| Human-confirmed material findings unique to each reviewer | Tests independent-review value without rewarding noise |\n| Finding precision (`accepted material findings / total findings`) | Penalizes nitpicking and disagreement theater |\n| Invalid RED attempts caught | Measures evidence-gate value |\n| Validator rejections and escaped defects | Measures gate effectiveness |\n| Credits/tokens, wall time, and model escalations | Measures cost and latency trade-offs |\n| Human decisions and decision time | Measures oversight burden |\n\nTargets for the pilot:\n\n- no decrease in hidden acceptance-test pass rate versus the all-frontier separated-role run;\n- at least 25% lower credit/token cost than the all-frontier run, reported as a goal rather than guaranteed outcome;\n- zero accepted invalid-RED records;\n- zero silent family-constraint or validator-gate bypasses; and\n- qualitative reviewer findings are counted only after human confirmation as material.\n\n“TDD preflight finds at least one gap” and “models disagree at least once” are **not** success gates; both would incentivize manufactured findings. A clean null result is valid data.\n\n### What hidden tests actually buy\n\nNot insulation from human bias — humans author the locked tests and the hidden tests, so the same blind spots ride along in both. Claiming otherwise would overstate the design.\n\nWhat they buy is **Goodhart protection**. The executor can see the locked tests, so it can satisfy their letter without the behavior generalising: special-casing the asserted input, implementing to the example rather than the rule. Hidden tests are the held-out set that detects exactly that gap. They measure whether the behavior was built or the test was beaten.\n\nThis is why hidden tests stay out of every agent's context, including the validator's — a validator that can see them can coach toward them.\n\n---\n\n## 14. Demo Narrative\n\nThree acts. Each one earns the next.\n\n### Act 1 — By hand. It works, and that's the problem.\n\nRun the method with the manual harness: two CLIs, shell glue, hash locking, evidence capture. It genuinely works — that is the point, and the reason the baseline must not be strawmanned.\n\nThen show the cost of it working:\n\n- **You are the orchestrator.** Every handoff is a human decision, so the process runs at the speed of your attention.\n- **The laptop stays open.** Close it and the run dies.\n- **Nothing is enforced.** Family separation, test locking, and validator independence are conventions the operator maintains. A tired operator silently degrades every one of them.\n- **No attribution.** Nobody can say what the run cost, or which role spent it.\n- **Nothing to show a CISO.** Evidence lives in scrollback.\n\nAn audience of engineers recognises this immediately, because it is what their teams are doing right now.\n\n### Act 2 — Push a button, go enjoy life.\n\nThe same sprint as a command-orchestrated script. Pinned models per role, hooks enforcing the locks, the orchestrator holding the run. Kick it off, close the laptop, come back to a completed sprint with an audit bundle. *(Note: the GO-NO-GO decision closed the Mission-native path. See Phase 4 Track C for the honest demo packaging.)*\n\nThen the beat that separates this from every \"autonomous agent\" demo: **it comes back to you only when your judgment is actually required.** Not a stream of approval prompts — batched decision packets at the points that matter (§6): an unresolved semantic disagreement, a course-changing chunk, a repeated rejection. Each one arrives with what changed, why the run paused, the competing positions, the evidence, and the cost of delay.\n\nAutonomy that never asks is reckless. Autonomy that asks constantly is just slower manual work. The product is autonomy that knows the difference — and the `oversight` setting lets a buyer dial exactly where that line sits for their risk tolerance.\n\nThe delta from Act 1 is the demo. Not \"AI wrote code\" — *the orchestration stopped being your job, and the guarantees stopped being your discipline.*\n\n### Act 3 — Now make it safe for a bank.\n\nAutonomy is the easy half; every vendor demos that. The reason a regulated buyer signs is the layer on top:\n\n- **Model rules and per-user overrides** — which models touch which work, enforced rather than requested\n- **Droid Shield** on the validation path\n- **Deployment flexibility** — SaaS, hybrid, on-prem for buyers who cannot send code out\n- **OpenTelemetry traces** — the run as auditable evidence, exportable into existing security tooling\n\n\"Push a button and go enjoy life\" is exactly what an enterprise buyer distrusts. Pairing it with this act is what converts it from a risk into a sale: *go enjoy your life, and here is why your CISO is fine with that.*\n\n> **Build Act 3 only on capabilities Phase 0 verified.** Probes 1–4 cover model pinning, fallback safety, context isolation, and deterministic hook blocking — demo those. Air-gapped deployment and the full software-factory outer loop are known to be immature; referencing them as roadmap is fine, staging a demo beat on them is not.\n\n### Close — honest, and stronger for it\n\nAgreement is not correctness.
