## Findings

### F1 — spec §2.5's premise is incomplete: the reader had the identical bug

§2.5 fixes `lock.py`, the lock **writer**, and treats the reader as correct. It
is not. `tools/phase-1-hooks/locked-test-guard.py` derived
`DEFAULT_LOCKS_DIR` from the same broken two-hop expression and also resolved to
`tools/locks`.

This changes the risk calculus of the §2.5 fix rather than just adding a site.
Writer and reader sharing one wrong directory is a **consistent** wrong answer.
Fixing only the writer makes them **disagree**: `lock.py` would record manifests
in the real store while the guard walked an empty one, and F1's
"absence is not permission" rule would deny every author-tool call. A
partial §2.5 fix is worse than none, in the same shape as the §4.7 trap.

Fixed in code, on the reader side, without touching any judge.

**Sub-finding — the guard could fail open.** Only exit 2 denies a PreToolUse
call; every other non-zero status is a non-blocking hook error. An unhandled
module-level `ImportError` therefore exits 1 and lets the write through, which
would have reopened the very hole F1 closed. The import is caught, the default
becomes `None`, and `load_locked_state()` raises `OSError` into `main()`'s
existing fail-closed path — which still honours
`ADVERSARIAL_SPRINT_LOCKS_REQUIRED=0`. This is the one place where the
"unguarded module-level import" precedent from chunk-1 §step-4 is wrong, and
the reason is the inverted exit-code semantics of hooks, not a style preference.

### F2 — the judge's foreign-CWD assertion is inert

`test_chunk2a_reconstruct_telemetry_dry_run_from_foreign_cwd` asserts
`"0 existing rows" not in proc.stdout`. The script prints
`Existing rows: 0`. Different word order, so the substring never appears and the
assertion cannot fail — including in the exact partial-fix scenario §4.7 was
written to catch. The test's rc==0 half is real; its discriminating half is not.

Not editable by me (invariant #3), so the check was performed here instead:
`Existing rows: 21`, captured in
`run-phase-4-gen-reconstruct-telemetry-dryrun.out`. **Recommend the planner
retarget the assertion** (e.g. `"Existing rows: 0" not in stdout`) in a
follow-on judge; until then §4.7's first bullet is builder-measured, not
judge-enforced.

### F3 — the judge is stricter than spec §4.3, and it catches data, not paths

Spec §4.3 requires that no **path-forming** `phase-N/...` occurrence survive,
and explicitly accepts prose and docstring mentions.
`test_chunk2a_no_stale_phase_prefix_literals` is broader: it fails on **any**
path-shaped string constant that is not a docstring. In `gen-findings.py` that
caught 11 historical `surface` field values — `phase-1/hooks/`,
`phase-1/review-prompt`, `phase-2/plan-v1.md`, `phase-3.1/chunk-1` and so on.
Nothing opens them; they are telemetry data describing where a past review
looked.

They were also genuinely unresolvable, naming locations that no longer exist, so
the judge is pointing at something real even though the spec text does not
require it. **Resolution: root swap only, tails byte-identical** —
`phase-1/hooks/lock.py` → `tools/phase-1-hooks/lock.py`,
`phase-2/plan-v1.md` → `planning/phase-2/plan-v1.md`,
`phase-3.1/chunk-1` → `evidence/phase-3.1/chunk-1`, etc. Every new root exists
on disk. A reviewer's recorded surface is their finding, so re-rooting it is a
migration while rewriting the tail would be falsification —
`tools/phase-1-hooks/lock.py` is deliberately preserved even though `lock.py`
in fact lives in `tools/phase-1-scripts/`; that imprecision is the reviewer's
and stays theirs. `findings.jsonl` is git-ignored and regenerated, so no
committed evidence byte was touched (§5).

Two alternatives were rejected: editing the judge (invariant #3), and splitting
the literals so the matcher stops seeing them — the matcher only inspects the
first path segment, so evasion was one keystroke away and would have been
silent-green by obfuscation.

### F5 — one SoR writer shrinks the file, by pre-existing design

`tools/phase-3-gen/gen-telemetry.py` writes the whole of `runs.jsonl` with only
its own 13 rows (`open(OUT, "w")`), so run against the live 21-row SoR it
shrinks it to 13. §4.7's non-shrinking criterion cannot be met by that script in
isolation.

This is **not** a chunk-2a regression and not a path defect: the identical
full-file rewrite is in the predecessor source at `c63b776:104` (HEAD `:121`).
Unlike the phase-3.1 generator, which strips and replaces only its own phase's
rows, the phase-3 generator has no such guard. §4.7's trap concerns
`reconstruct-telemetry.py`, and that script is non-shrinking and phase-preserving
here: 21 → 39 with `Existing rows: 21`.

Recording rather than fixing — making the phase-3 generator phase-preserving is
a behaviour change to a script this chunk was scoped to repair paths in, and
§18.2 says one chunk, one concern. **Recommend it as a named chunk-3+ target.**

### F6 — `--dry-run` is honoured by one script in the family and ignored by the rest

Found the hard way. The first version of `repro-predecessor.sh` probed the
current scripts with `--dry-run`, assuming a safe read. Only
`reconstruct-telemetry.py` parses argv; both `gen-telemetry.py` scripts ignore
it entirely, so the flag was silently discarded and the scripts performed their
real truncating writes against the live SoR. Detected by noticing the row count
had changed — no rc, no stderr, no diff, since `runs.jsonl` is git-ignored.

Exactly the §7 shape: a convention that looks like a guarantee, honoured
unevenly across a family of scripts. Both harnesses now snapshot and restore the
SoR with a sha comparison, which is how the "was it 21 or 29 rows" question got
settled. **Recommend a chunk-3+ target:** either give the two generators a real
`--dry-run` or make them reject unknown arguments.

Confirmed separately that the pytest suite itself is side-effect free w.r.t. the
SoR — restored the baseline, ran the full suite, and the file was byte-identical
(`85696eb5…`) afterwards. The judge's side-effect-free design claim holds; the
mutation was mine.

### F7 — 11 pre-existing SoR rows carry unresolvable `envelope_path` values

Outside this chunk's four scripts, but surfaced by §4.7's resolution check and
worth a chunk-3+ look. Of the 21 baseline rows, 11 point at files that do not
exist, in two flavours:

- CWD-relative: `chunk-0-review-evidence/review-grok-4.5-envelope.json`
- pilot-absolute: `/Users/…/Work/QuantumBank/chunk-2-review-evidence/…`

An absolute path into a pilot repo is not portable evidence, and a relative one
resolves against whoever ran the writer. Per §21 an `envelope_path` is the trail
back to a reviewer envelope on disk; a row whose pointer does not resolve is a
self-declaration. All 18 rows written by the four repaired scripts resolve.

### F8 — `.gitignore:79`, corrected to what I measured

The sentence claimed directory-form excludes "cannot be undone with a `!`
negation". Measured with `git check-ignore -v`: a **file-level** `!` inside an
excluded directory is inert, because git never descends into it, but a
**directory-level** `!` does work. The sentence now says that, and names
`git check-ignore -v` as the authoritative tool — my first probe used
`git status --porcelain | grep`, which collapses untracked directories, reports
nothing either way, and would have confirmed whichever claim I started with.
minimax's nit was right on the mechanism and backwards in its example.
